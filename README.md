# b3-all-in-one

SaaS platform combining a tax-aware B3 backtest bench with portfolio self-care and IRPF.
Full spec in `spec/`. Local-only for now: everything runs via docker compose, no deploys.

## Layout

- `spec/` — the platform spec (read `spec/00-overview.md` first)
- `engine/` — vendored from `b3-pipeline-data-and-backtest-framework` (data pipeline +
  backtest engine + Rust COTAHIST parser). Being ported SQLite → Postgres.
- `taxcore/` — vendored from `b3-portfolio` (B3 extract parsing, IRPF engine, TLH,
  methodologies), including synthetic data fixtures for golden tests.
- `platform/` — the new FastAPI application (auth, tenants, jobs, API).

## Test fixtures are synthetic

The B3 extracts under `taxcore/b3_imports/`, the CSVs derived from them and the IRPF
golden are **fabricated** — generated by `taxcore/tests/golden/make_fixtures.py` from
literal tables. Only the ticker symbols and institution names are real (public market
data), so the synthetic positions can be priced from the vendored Fundamentus
snapshots. See `taxcore/tests/golden/README.md`.

## Quickstart

```
cp .env.example .env
docker compose up -d postgres              # infra only
docker compose --profile app up --build -d # + api & worker (self-contained images)
```

The images bake in taxcore's code (`scripts/`, `methodologies/`) and its deps in a
separate venv at `/opt/taxcore`, plus the backtest engine's code (`b3_pipeline/`,
`backtests/`, `scripts/`) and its deps at `/opt/engine`, so the import → portfolio →
IRPF loop AND the backtest bench run entirely inside the containers — no host
`../taxcore`/`../engine` checkout needed. taxcore's **data** (`b3_imports/`, `data/`,
`reports/`, `tests/`) and the engine's **data/db/tests** are deliberately kept out of
the image — backtests read the market plane from Postgres, not from files.

### Backtest bench

- `GET /strategies` — the strategy gallery (name, kind `code`|`spec`, params/defaults).
  Cached in-process; discovery runs inside the engine venv.
- `POST /backtests {strategy, params?, start?, end?, freq?}` — queues a run; the worker
  shells into the engine venv (`scripts/run_backtest_json.py`), stores metrics on the
  row and artifacts (`metrics.json`, `curves.csv`) under `ARTIFACTS_DIR/{run_id}/`
  (shared `artifacts_data` volume, mirroring `uploads_data`).
- `GET /backtests`, `GET /backtests/{id}`, `GET /backtests/{id}/curves` — history, a run
  row + metrics, and the pre/after-tax equity + drawdown + turnover series.
- `GET /market/status` — price-plane row count, distinct tickers, min/max date, and
  per-table freshness for `corporate_actions`/`fundamentals_pit` (0-row tables reported
  honestly).

**Network:** a backtest run fetches **CDI daily from the Brazilian Central Bank**
(`api.bcb.gov.br`, required by `build_shared_data`, reliable) and nothing else.
**Benchmarks come off the plane**, not Yahoo: `^BVSP` resolves to `$IBOV` and the
ETF sleeves to their own COTAHIST tickers, so IBOV is a real series now instead of
a flat stub. Set `ENGINE_BENCH_OFFLINE=1` (compose sets it on api+worker;
`platform/tests` set it too) to stub CDI and the benchmarks and run fully offline —
valid for price-only strategies (`LowVol`, `MomSharpe`, …). ETF/regime strategies
need the real series and are not supported on the offline path.

On boot the **api** runs `alembic upgrade head` before uvicorn (via the entrypoint,
gated on `RUN_MIGRATIONS=1`); the **worker** applies its own procrastinate schema.
Uploaded files land on a shared `uploads_data` volume mounted into both services at
`/data/uploads`, so files the api saves are visible to the worker's import jobs.

### Portfolio benchmarking (spec/03)

Two complementary answers to "how am I doing?", both off the tenant's own book:

- `GET /portfolio/index` — the book the user *actually* holds as a daily
  time-weighted index (base 100) against IBOV and CDI. Holdings are rebuilt from their
  trades + qty_events, valued at the market plane's raw closes; deposits and withdrawals
  move the NAV but not the line, and proventos count as return the day they land. The
  response's `excluded` block names everything the index could not see (Futuro, Renda
  Fixa, unpriced tickers) and `coverage.clamped` says when the chart starts later than
  the user's real history because the plane does. Benchmarks come from the engine
  (`scripts/bench_series.py`); with `ENGINE_BENCH_OFFLINE=1` they are reported
  unavailable rather than drawn flat.
- `POST /whatif` — the same money through a *different* strategy (spec/05 Feature 2).

### Strategy-linked portfolio (spec/05)

Attach strategies to the portfolio as fixed-percentage sleeves, then get told what to
buy/sell to rebalance — tax-optimally. All prices come from the engine market plane
(`advise_weights.py`, latest `raw_close`); tax runs through taxcore's TLH machinery.

- `GET/PUT /portfolio/sleeves` — sleeve config `[{strategy_ref, target_pct}]`, validated
  to sum to 100 (`CASH_CDI` is the risk-free sleeve; everything else a gallery spec).
- `GET /portfolio/target` — the combined target: each strategy sleeve's advised weights
  (blended `Σ pct/100 × weights`) plus `cash_weight_target` from `CASH_CDI`, the current
  weights from the priced book, and per-ticker `drift`. `409` when no sleeves configured.
- `POST /portfolio/rebalance-plans {new_cash?, exclude?, pins?}` — advisor v0
  (single-shot, this month): combined target → integer trade list → tax overlay
  (per-class situation, isenção usage, harvest + T+1 rebuys). Pinned/excluded tickers are
  held in place (dropped from both sells and buys); `notes` flags e.g. an ações month
  above the R$20k isenção. Advisory only — nothing executes.

### Billing (Stripe, spec/01)

Three tiers — `gratis` < `investidor` (R$29/mês) < `trader` (R$79/mês). Entitlements
live on the tenant row (`user.plan` + `plan_status`) and are written **only** by the
webhook: checkout hands back a URL, it never grants access.

- `GET /billing` — effective plan, status, renewal date, whether a portal exists.
- `POST /billing/checkout {plan}` — hosted Checkout session → `{url}`.
- `POST /billing/portal` — Stripe billing portal (card, invoices, cancel, downgrade).
- `POST /billing/webhook` — signature-verified; `customer.subscription.*` drives the
  plan. Events older than the last applied one are dropped (Stripe doesn't order them).
- `POST /billing/dev-plan {plan}` — **development only**, flips the plan without
  Stripe so the paywall is testable locally.

What each tier unlocks (gated routes answer `402` with
`{"error": "plan_required", "required_plan", "current_plan"}`; the frontend turns any
402 into the upgrade dialog):

| Tier | Routes |
|---|---|
| `gratis` | `/imports`, `/portfolio/{positions,trades,income,price-history}`, `/market` |
| `investidor` | `/irpf`, `/tlh`, `/whatif`, `/portfolio/{sleeves,target,rebalance-plans,settings,index}` |
| `trader` | `/backtests`, `/strategies/user*` |

`GET /strategies` (the gallery) stays public. The dev tenant is created on `trader` so
seeding and tests aren't paywalled — `dev_seed.sh` re-asserts it on every run.

Local loop with the Stripe CLI (test mode; keys in `.env`, price ids in `.env.example`):

```
stripe listen --forward-to localhost:8000/billing/webhook   # prints the signing secret
stripe trigger customer.subscription.updated                # or drive a real sub:
stripe subscriptions create --customer cus_… -d "items[0][price]=$STRIPE_PRICE_TRADER"
```

### Privacidade / LGPD (spec/08)

The data-subject rights of art. 18 are routes, not a support mailbox — free at every
tier, scoped to the **account** (its own book plus every client book it manages):

- `GET /privacy/summary` — confirmação do tratamento: what is stored, counted per book.
- `GET /privacy/export` — acesso + portabilidade: every row of every book, as JSON.
- `DELETE /privacy/account` — eliminação: rows, uploaded extracts, backtest artifacts,
  the Stripe customer and the login itself. Irreversible, and it frees the email.

Both the export and the erasure discover their tables from `Base.metadata` (any table
with a `tenant_id`), so a new tenant table is covered without touching either — and
`platform/tests/test_privacy.py` seeds all of them to keep that honest. The frontend
serves this at `/conta`; the public policy lives at `/privacidade`.

## Frontend (local)

Next.js (App Router) + TypeScript + Tailwind in `frontend/`. Talks to the API at
`NEXT_PUBLIC_API_URL` (default `http://localhost:8000`); CORS already allows
`http://localhost:3000`.

```
docker compose --profile app up -d   # 1. bring the API up (http://localhost:8000)
./scripts/dev_seed.sh                # 2. seed a dev tenant (imports + sleeves + a backtest)
npm --prefix frontend install        #    first run only
npm --prefix frontend run dev        # 3. dev server on http://localhost:3000
```

**Login:** open `http://localhost:3000`, click **Entrar (dev)** — this hits
`POST /auth/dev-login`, stores the JWT in `localStorage`, and every request is sent with
`Bearer` auth. The sidebar footer shows API health, market-data freshness, the logged-in
email, and a **sair** (logout) action. Google OAuth comes later.

`scripts/dev_seed.sh` is idempotent (imports full-replace the portfolio) and prints a
backtest summary at the end. `npm --prefix frontend run build` runs a clean production
build.

## Quality gates

The suites are the contract, not the review. Eight checks run in CI
(`.github/workflows/ci.yml`) — the six gates, plus the unit suites and the lint they
sit on:

| Gate | What runs | Where the threshold lives |
| --- | --- | --- |
| Unit tests | `pytest` per package, `node --test` for the frontend | — |
| Lint | `npm run lint` (eslint, green) | `frontend/eslint.config.mjs` |
| Gherkin specs | `taxcore/tests/features/*.feature` via pytest-bdd | the feature files |
| Coverage floor | `pytest --cov-fail-under` | `ci.yml`: platform 75, engine 60, taxcore 20 |
| Cyclomatic complexity | ruff `C901` (Python) + eslint `complexity` (TS), max 10 | `scripts/quality_gates.py` + baseline |
| Module size | max 400 lines (`.py`, `.ts`, `.tsx`) | `scripts/quality_gates.py` + baseline |
| Dependency boundaries | AST import contracts | `CONTRACTS` in `scripts/quality_gates.py` |
| Mutation testing | `mutmut` over `taxcore/scripts/apuracao.py`, max 6 survivors | `ci.yml` |

**The two structural gates are ratchets, not walls.** The repo has 63 functions over
complexity 10 (45 Python, 18 TSX) and 28 modules over 400 lines today;
`scripts/quality_baseline.json` records every one. A PR fails if a baselined offender
gets worse or a new one appears — never for the debt that was already there. After a
genuine improvement:

```
npm --prefix frontend ci                   # once; eslint is half the complexity gate
python scripts/quality_gates.py            # check, as CI does
python scripts/quality_gates.py --update   # re-record; the baseline only goes down
```

Without `frontend/node_modules` the script prints `SKIPPED` for the frontend half and
drops those entries from the comparison rather than reporting them clean; `--update`
refuses outright, so a partial run can never quietly erase them from the baseline.

**Coverage is 80 / 62 / 22% (platform / engine / taxcore), not 100.** The floors are
below today's numbers so they can only rise; raise them in `ci.yml` whenever a PR
clears one. The taxcore number is the honest one to fix first — most of
`taxcore/scripts` is CLI entrypoints with no test at all.

Platform is measured with `COVERAGE_CORE=sysmon` (PEP 669). That is not cosmetic: the
default `sys.settrace` backend taxed an upload handler from ~170ms to 424ms and broke
the suite's wall-clock assertions on event-loop responsiveness. It also reads ~8pp
higher, because it sees lines executed in `asyncio.to_thread` workers that the trace
hook misses — which is why that floor moved 70 → 75.

**The Gherkin specs are in Portuguese on purpose.** They cover the apuração rules
(isenção de R$ 20.000, alíquotas, compensação de prejuízo) — the part of this repo a
contador has to be able to check without reading Python. `tests/test_apuracao.py` is
the fine-grained unit suite; the feature file is the readable contract on top of it.

**Mutation testing is scoped, and it is a real gate on every PR.** Target:
`taxcore/scripts/apuracao.py`, the isenção / alíquota / compensação rules, against the
two apuração suites — 96 mutants, **90 killed and 6 surviving**. The whole job is ~20s
in CI (12s of that mutating); it is on the PR path because it is that cheap, not
despite it.

The gate earned its place on the first run: it found that nothing covered two
consecutive loss months in one bucket, so `carry += -pnl` could become `carry = -pnl`
undetected. On the reviewer's example that under-reports the accumulated loss by
R$ 5.000 and over-collects R$ 750 of IR. Also unlabelled: sub-R$1 gains (`pnl > 0` vs
`pnl > 1`) and break-even months. Those tests are now in `tests/test_apuracao.py`.

The 6 that remain are all **equivalent mutants** — each flips a comparison in a way
that only differs at `pnl == 0`, where the two branches do the same arithmetic
(`carry += -0.0` and `base = 0 - 0` are both no-ops):

```
41 `pnl > 0`→`pnl >= 0`   44 `pnl < 0`→`pnl <= 0`   45 `pnl < 0`→`pnl < 1`
49 `pnl > 0`→`pnl >= 0`   61 `pnl < 0`→`pnl <= 0`   62 `pnl < 0`→`pnl < 1`
```

No test can kill them, so 6 is the bound the job enforces: it reads
`mutmut export-cicd-stats` and fails at 7. A seventh survivor is a real hole in the
apuração suite. If `monthly_apuracao` changes, re-check the equivalence argument above
rather than just raising the bound.

The other clauses all guard one failure — the gate going green having tested less than
it claims — because `survived` alone is easy to hold at 6 while the work disappears:

- **`no_tests == 0`** — a mutant no test even *executes*. Those are not survivors, so
  an uncovered new branch in `monthly_apuracao` would otherwise sail through.
- **`total >= 96`** — a *falling* mutant count needs a human, whatever the cause. One
  `# pragma: no mutate` on the `isento` line deletes 6 mutants of the R$20.000
  boundary; measured, every other clause stays green. Raise the floor when
  `apuracao.py` legitimately grows.
- **`killed + survived + timeout == total`** — `mutmut`'s `Stat` has 11 fields and the
  exported JSON writes 9, while `total` sums all 11. Two buckets are therefore counted
  in a key you never see, and no `X == 0` clause can cover a key that isn't in the
  file. Only the arithmetic can.
- **`suspicious`, `segfault`, `skipped`, `check_was_interrupted_by_user`** — fate
  unknown, which is the same as untested.

`timeout` is deliberately *not* gated: a timeout usually means the mutant hung, so the
suite would have killed it, and it is the one bucket a slow runner can move things into
— gating it would trade a real hole for a flake.

`mutmut run` itself exits 0 with survivors, so it cannot be the gate — that is why the
count is checked explicitly instead of relying on the exit code.

Those rules live in their own module *because* of this gate: mutmut writes every
mutant of a module into one file, and pointed at the 1100-line `irpf_2026.py` it
produced a 42 MB, 745k-line module that never finished importing. Keep the target
small. Widen `source_paths` in `taxcore/pyproject.toml` one small module at a time,
not by pointing it at a directory.
